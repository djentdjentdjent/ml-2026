# Проект «Анализатор путевых листов»
**Период:** 06.10–12.10.2026

**Автор:** Степанов Андрей  

**Тема проекта:** Разработка веб-приложения для автоматического извлечения структурированных данных из путевых листов на основе детекции ключевых зон с помощью моделей компьютерного зрения.

**Задача:**  
Создать программный продукт, который принимает на вход изображение путевого листа (форма № 3, упрощённая форма или аналог) и возвращает структурированные данные — ключевые поля, извлечённые из документа.

**Ключевая особенность подхода:**  
В отличие от классического OCR-пайплайна (распознавание всего текста → поиск по регулярным выражениям), в проекте применяется двухэтапный ML-пайплайн:

1. **Детекция ключевых зон** документа обученной моделью object detection (YOLOv8).
2. **Распознавание текста** только в вырезанных областях с помощью OCR-модуля (EasyOCR).

Такой подход позволяет существенно повысить точность извлечения полей за счёт снижения влияния «шума» (таблицы, печати, рукописные вставки, лишний текст) на этап распознавания.

**Актуальность предметной области:**  
Путевые листы — ключевой документ первичного учёта в транспортных компаниях, автопарках и организациях с собственным автохозяйством. Их обработка вручную трудоёмка, подвержена ошибкам и плохо масштабируется. Открытых качественных решений для автоматического парсинга именно российских путевых листов на текущий момент практически не существует, что делает проект оригинальным и практически ценным.

## 2. Цели и задачи проекта

**Цель:**  
Получить практические навыки построения full-stack ML-приложения: от сбора и разметки данных до обучения модели, её интеграции в backend и развёртывания в виде работающего веб-сервиса, применительно к задаче автоматизации обработки путевых листов.

**Задачи:**

1. Сформировать датасет изображений путевых листов с разметкой bounding boxes для ключевых полей (собственный датасет: реальные сканы + синтетические данные).
2. Обучить модель детекции объектов (YOLOv8) на подготовленном датасете.
3. Реализовать ML-пайплайн инференса: детекция → crop → предобработка → OCR → постобработка.
4. Разработать backend (FastAPI) с REST API для приёма изображений и возврата результатов.
5. Разработать frontend (HTML + JavaScript) с интерфейсом загрузки и визуализации результатов.
6. Провести оценку качества модели: посчитать метрики детекции (mAP, precision, recall) и метрики извлечения полей (F1), сравнить с baseline-подходом (OCR всей страницы + Regex).
7. Упаковать решение в Docker-контейнеры и подготовить документацию.

## 3. Минимальный пользовательский сценарий (MVP)

Пользователь загружает изображение путевого листа (JPG/PNG) → система возвращает JSON со следующими полями:

| Поле | Описание | Пример значения |
|---|---|---|
| `doc_number` | Номер путевого листа | `147` |
| `doc_date` | Дата выдачи | `07.10.2026` |
| `vehicle_plate` | Государственный регистрационный знак ТС | `А123БВ 77` |
| `driver_name` | ФИО водителя | `Иванов И.И.` |

Дополнительно пользователю отображается исходное изображение с наложенными bounding boxes и подписями распознанных полей.

Распознавание маршрута, показаний спидометра, расхода топлива, печатей и подписей в MVP не входит (планируется в следующей итерации).

## 5. Архитектура MVP

```
Пользователь
     ↓
 Frontend (HTML + JavaScript)
     ↓ изображение путевого листа (multipart/form-data)
 Backend (FastAPI)
     ↓
 ┌──────────────────────────────────────────────────────┐
 │  ML-пайплайн (модуль ml/)                            │
 │  1. YOLOv8 (детекция ключевых зон)                   │
 │  2. OpenCV (crop + бинаризация Otsu + выравнивание)  │
 │  3. EasyOCR (распознавание текста в зоне, lang=ru)   │
 │  4. Постобработка (валидация форматов, regex)        │
 └──────────────────────────────────────────────────────┘
     ↓
 JSON с извлечёнными полями + визуализация
     ↓
 Frontend
```

**Стек технологий:**

| Слой | Технологии |
|---|---|
| ML | PyTorch, Ultralytics YOLOv8, EasyOCR, OpenCV, NumPy |
| Backend | Python 3.11+, FastAPI, Uvicorn, Pydantic |
| Frontend | HTML5, JavaScript (vanilla), CSS3 |
| Хранение | PostgreSQL (история запросов), локальное хранилище для моделей |
| Контейнеризация | Docker, docker-compose (отдельные образы для ML и backend) |
| Генерация данных | Pillow, ReportLab, Faker (для синтетического датасета) |

## 6. Датасет и модель

### 6.1. Датасет

В отличие от исходного плана (SROIE/CORD), для задачи парсинга путевых листов открытых размеченных датасетов не существует. Применяется **гибридный подход**:

| Источник | Объём | Назначение |
|---|---|---|
| **Реальные путевые листы** (собственные) | 5–20 сканов | Эталонная структура, ручная разметка, валидация |
| **Синтетические путевые листы** (генератор на Python) | 300–500 изображений | Основной объём для обучения YOLOv8 |
| **Аугментации** (Ultralytics встроенные) | ×3–5 к объёму | Повышение робастности (поворот, шум, яркость) |

**Генератор синтетики** создаёт изображения путевых листов на основе шаблона (форма № 3 / упрощённая форма) с рандомизированными данными через библиотеку `Faker` (ФИО, номера авто, даты) и автоматически сохраняет точные bounding boxes в формате YOLOv8.

**Требуемые классы разметки:** `doc_number`, `doc_date`, `vehicle_plate`, `driver_name`.

**Минимальный объём:** 150–200 изображений после аугментаций.

### 6.2. Модель

**Детекция:** YOLOv8n / YOLOv8s (Ultralytics) — предобученная на COCO, дообучается (fine-tune) на целевом датасете путевых листов.

**OCR:** EasyOCR (язык — только русский, `ru`).

**Постобработка:**
- Валидация даты: regex `\d{2}\.\d{2}\.\d{4}`
- Валидация гос. номера: regex `^[А-Я]\d{3}[А-Я]{2}\s?\d{2,3}$`
- Очистка ФИО от артефактов OCR
